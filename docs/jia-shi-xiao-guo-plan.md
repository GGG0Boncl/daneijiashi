## 0. 先回答"能不能训练多个 Agent"

| 能力 | 结论 | 怎么做 |
| --- | --- | --- |
| 六部各自独立（人格/记忆/权限/产出） | ✅ 能 | 每部一份 persona JSON + 独立记忆目录 + 独立工具白名单 |
| 六部定时自主出奏疏 | ✅ 能 | 复用中枢已有的定时/接口层，按部注册任务 |
| 御书房批阅（朱批/留中/驳回/问询） | ✅ 能 | 奏疏状态机 + 批示存档 + 回奏 |
| 帝后合议、冲突不站队 | ✅ 能 | 指令状态 `awaiting_council`，未合议不许下发 |
| 越权拦截 | ✅ 能 | 每部 allowlist：能读什么、能改什么，越权直接 403 |
| 越用越懂你家 | ✅ 能（教练闭环） | 例库 + 5 条评分 rubric + 回归跑分，改 prompt 不提权重 |
| 真·微调模型权重 | ❌ 做不到 | 无训练环境；家庭场景也不需要 |
| 古风文风 100% 稳定 | ⚠️ 不能保证 | 用 rubric 约束 + 少样本例库压到"稳定够用" |

**结论**：能做出"像训练过"的多 Agent 家国系统，但训练的是 **prompt + 例库 + 评测**，不是权重。

## 1. 架构：在现有三件套上加一层"朝廷"

```
安卓 App（新增「御书房」页）──HTTP──  中枢 hub（新增 court 模块）
                                        ├─ 六部 Agent 运行时（persona + 记忆 + 工具白名单）
                                        ├─ 奏疏 / 批示 / 圣旨 存档（court/*.json）
                                        ├─ 定时任务：07:30 / 21:30 触发吏部
                                        ├─ 司礼监摘要器
                                        └─ DeepSeek 调用（复用现有指纹缓存，省 token）
```

**关键原则：现有打卡/日历/提醒/复盘一行都不改**，家国层只是"读数据 + 出奏疏"，出问题是可降级的。

## 2. 数据模型（新增目录，不动 records）

```
data/court/
  personas/<部>.json        # 该部 system prompt + 权责 + 禁则 + 输出格式
  memorials/<id>.json       # 奏疏：部、标题、正文、状态、批示、指纹
  edicts/<id>.json          # 圣旨 / 懿旨 存档
  memory/<部>/notes.json    # 该部自己的记忆（既往结论、被驳回的原因）
  gym/<部>/cases.json       # 训练例库（指令 → 期望要点）
  gym/<部>/rubric.md        # 5 条评分标准
```

奏疏状态机：`pending`（待阅）→ `approved`（朱批）/ `held`（留中）/ `rejected`（驳回+批注）/ `counciling`（帝后未合议）。
**任何方案生效前，六部不许自己改任何数据**——这条写进 prompt 也在服务端拦。

## 3. 六部映射（能力从哪来）

| 部 | 现有能力可复用 | 需要新增 | 第一阶段是否做 |
| --- | --- | --- | --- |
| 吏部（考成） | ✅ 打卡/提醒/统计/复盘 | 轮岗表（可后置） | **做** |
| 司礼监（文书） | ✅ 素材包 + 缓存 | 摘要器 | **做**（很轻） |
| 户部（钱粮） | — | 极简记账（一句文字 → 解析成流水） | 二期 |
| 礼部（仪制） | ✅ 日历/提醒 | 纪念日 + 朝会议题 | 三期 |
| 工部（营缮） | — | 家务排班/维修清单 | 三期 |
| 兵部（安防） | ✅ 提醒 | 巡检清单 | 四期 |
| 刑部（调解） | — | 陈情表单（双方各写一段） | 四期 |

## 4. "训练"是怎么落地的（Agent Gym）

每部一套：

1. `cases.json`：10 条典型指令（真实家庭场景），每条给"期望要点"（必须提到数据、必须给方案、不许越权…）。
2. `rubric.md`：5 条硬标准，逐条打分：`越权? 引用数据? 给方案? 等批示? 文风可读?`
3. `tools/court-train.mjs --dept libu --rounds 3`：
   跑用例 → 打分 → 打印失分点 → 改 prompt → 再跑 → 记录分数曲线。
4. 结果存 `gym/<部>/history.json`，能看出"这一部这几轮变强了还是退步了"。

> 这就是"独自训练多个 Agent"的现实版：**每个部都有自己的训练场和分数**，越练越贴自家，但不会动模型权重。

## 5. 安全与边界（文档要求，全部落代码）

1. **页脚声明（已按用户要求撤下）**：原计划在页脚常驻「家庭角色扮演…」一行；
   用户 2026-11-18 明确要求不要把这些开发设定写进界面，App 里已删除，只保留在服务端配置字段里备查。
2. **批阅权限锁**：只有 `role: emperor|empress` 的成员能批；其他人只能交目标/打卡/陈情（服务端校验，不靠前端）。
3. **越权拦截**：每部有 `allowRead/allowWrite` 清单；例如户部改不了考成，刑部判不了考核。
4. **成本闸门**：复用分析缓存思路——同一份数据 + 同一部 + 同一任务，奏疏指纹不变就不重复生成；每人每天最多 N 次主动召唤。
5. **不上云端**：所有数据仍只在家里电脑，奏疏也只存本地。

## 7. 我打算怎么开工（P1）

1. 中枢新增 `court/` 模块：persona 加载、奏疏 CRUD、批阅状态机、回奏。
2. 吏部第一个：`POST /api/court/summon {dept:'libu'}` → 读打卡数据 → 生成奏疏（带数据指纹缓存）。
3. App「御书房」页：奏疏列表 + 详情 + 四个批示按钮 + 批示历史；底部常驻平等声明。
4. 测试：fake 模型跑「生成→批阅→回奏→越权拦截→缓存命中」全链路。
5. 用你现有的两位成员 + 真实数据，生成第一份《全员考成簿》给你看。

| --- | --- |

| `court/context.mjs` | 各部分领域数据摘要（吏部接打卡统计、户部接流水、礼/兵/刑/工接台账、司礼监接待批奏疏） |

| `court/agents.mjs` | summon（指纹缓存，同数据不重复花钱）、dispose、reply（回奏）、meeting（朝会，不走模型） |

| App「御书房」 | 第 4 个 tab：身份徽章、七部召唤按钮、召集朝会、一句话记账、奏疏列表与详情、四个批示按钮、常驻平等声明 |
